# 投稿画面の簡略化と画像の保存制御

2026年9月6日。ローカル実装のみ、本番未反映です。

## 投稿の流れ

- 本文を入力し、必要なら写真1枚かURLを追加して「投稿する」。タイトル入力・毎回の公開確認チェックはありません。「投稿は誰でも読めます」と短く表示します。
- 投稿種別は小さい選択欄。通常は「投稿」、教材から来た場合は「質問」、ノート共有は元の種別を保ちます。
- 表示名の初期値と、公開プロフィールの紐付けは分離。非公開プロフィールを勝手に公開しません。
- 既存のAPI公開条件は維持し、明示的な送信操作で`publicConsent:true`を渡します。プロフィール公開や規約同意まで省略するものではありません。
- タイトル未指定時は本文先頭から100 UTF-16文字以内で生成。旧タイトル付き投稿を維持し、再送比較より先に正規化します。
- URLは本文末尾にまとめ、HTTP(S)だけをリンク表示します。サーバーで外部URL・画像・リンク先の情報を取得しません。
- 投稿に失敗してもフォームを維持。画像保存済みなら同じIDで再試行し、期限切れならIDだけ外して再送時に画像を追加し直します。

## 画像の上限

`lib/community-media-limits.ts`で一元管理。新規保存にのみ適用します。

| 対象 | 初期上限 |
| --- | --- |
| 投稿への添付 | 1枚 |
| 保存する画像 | 500,000 bytes、最大辺1,200px |
| 会員1人の保存容量 | 50,000,000 bytes |
| サイト全体の保存容量 | 2,000,000,000 bytes |
| 直近24時間のアップロード | 1人20枚 |
| まだ使っていない画像 | 1人5枚 |

入力は12MB以下のPNG/JPEG/WebP。ブラウザーでPNGへ縮小し、上限以下になるまで段階的に再縮小します。サーバーでも容量・寸法・CRC・展開サイズを確認し、付帯情報を除去します。HEIC/GIFには対応していません。PNG方式のため写真によっては解像度が下がります。

投稿画像は選択時にはブラウザー内で準備するだけで、投稿ボタンを押したときに送信します。プロフィール写真の従来の仮保存・確定操作は維持します。

容量判定と予約行INSERTを1つのSQLにして、同時保存による上限超過を防止します。未使用画像・R2削除待ちも容量へ算入します。上限時は新規画像保存を止め、過去の投稿写真は自動削除しません。

24時間以上の未使用画像は、次のアップロード時に最大10件ずつ回収します。投稿（削除済みを含む）・非公開を含むプロフィール写真の参照は保護します。未使用画像を削除待ちテーブルへ移す処理と元行削除は同一トランザクション。R2削除失敗時も保存先を失わず再試行します。アップロード失敗時は24時間を待たず削除待ちへ移します。定期ジョブではありません。
